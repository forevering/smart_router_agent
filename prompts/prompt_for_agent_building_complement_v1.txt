新增补充要求：MCP 与基于向量的 Tool Retrieval 架构

1. 工具管理 (Tool Management)：
   - 废弃硬编码 API 描述的方式。
   - 实现一个 ToolRegistry 类作为所有工具的注册中心。
   - 每个 Tool 必须包含 name, mcp_server_name, schema(需兼容 LangChain的 Pydantic 或标准 JSON Schema 格式) 以及 search_document (包含描述和几个典型 Use Case 字符串)。
   - ToolRegistry 启动时，需将所有 Tool 的 search_document 转为 Embedding 并存入内存向量库 (如 FAISS 或简单的 Cosine Similarity 计算器)。
   - 持久化向量库：Tool 的 search_document (包含描述和典型 Use Case) 及其 Embedding 必须存储在持久化的 Vector DB 中（如持久化目录的 ChromaDB），确保 Agent 重启后向量数据不丢失。
   - 每个 Tool 在注册表中必须映射记录 name, mcp_server_name, schema (需兼容 LangChain Pydantic/JSON Schema 标准)。

2. 节点更新：Tool Retriever Node：
   - 在 Router 节点执行前，增加/合并一个工具检索逻辑。
   - 必须先结合用户的 Query、拉取到的 LTM 和 KG 状态，使用一个轻量级的 LLM 生成一段 contextualized_query (例如："结合已知信息[下周去上海]，用户询问下周旅行天气")。目的是改写用户query，让改写后的query能更好地携带上下文信息。
   - 使用 contextualized_query 的 Embedding 在 ToolRegistry 中检索 Top-K (如 Top-3) 最相关的 Tools。

3. 节点更新：Router Node：
   - Router 的 Prompt 保持通用，不再包含具体工具描述。
   - 必须使用 langchain/langgraph生态的工具动态绑定 Top-K 工具。需在 Prompt 中明确告诫 Router：只调用真正能解决当前问题的工具，忽略不相关的召回工具。
   - 返回结果必须是标准的 Tool Call 请求。



4. 节点更新：原 api_executor 重构为 mcp_executor (通用工具执行节点)：
   - 该节点现在必须是一个通用的 MCP 客户端代理 (MCP Client Proxy)。
   - 动态路由执行：
     1. 从 Router 节点生成的最后一条消息 (AIMessage) 中提取出所有的 tool_calls。
     2. 遍历每一个 tool_call，提取出 tool_name 和对应的参数 arguments。
     3. 通过前面定义的 ToolRegistry，查找该 tool_name 属于哪一个底层的 mcp_server。
   - 模拟 MCP 调用标准：实现一个模拟的 mcp_call(server_name, tool_name, arguments) 函数，代表通过标准化协议向外部 MCP Server 发起 RPC 调用。
   - 状态更新规范：将每个工具的返回结果严格封装为 LangChain/LangGraph 标准的 ToolMessage(content=..., tool_call_id=..., name=...)，并追加到 messages 状态流中，确保 generator 节点能够正确读取并融合这些外部工具的执行结果。

5. 工具的热插拔、多对一关系与热更新机制 (Hot-Reload)：
   - 多对一架构：明确 Tool 与 MCP Server 的关系。一个 MCP Server 可以包含多个 Tools。Agent 只需维护一个已订阅的 mcp_servers_config（记录了 Server 的连接地址或名称）。
   - 数据面与控制面分离：Agent 的对话路由属于“数据面”；必须额外设计一个轻量级的 `AdminController`（管理控制端类/接口），充当“控制面”，用于接收外部的变动通知。
   - 解耦与动态同步 API：Agent 主程序必须与工具代码解耦。在 ToolRegistry 中实现一个 sync_mcp_server(server_name) 的核心方法，用于在 Agent 不重启的情况下进行热更新。区分“新增”与“更新”的触发逻辑**：在 `ToolRegistry` 或 `AdminController` 中实现两个不同的核心方法，用于 Agent 主程序不重启的情况下的热更新：
   - 1. 新增 Server (`register_new_mcp_server(server_name, connection_config)`)**：接收新服务器的名称和连接地址。记录到系统配置中，然后向该地址发请求获取 `tools/list`，生成并存储新工具的 `search_document` Embedding。
   - 2. 刷新现有 Server (`refresh_mcp_server(server_name)`)：根据已有的 Server 记录，重新拉取 `tools/list`。对比本地持久化记录，找出新增或修改的 Tools，生成新的 Embedding 并Upsert（增量覆盖）到持久化 Vector DB 中。

6. Prompt 的配置化管理与解耦 (Prompt-as-Config)
   - 严禁硬编码：系统内所有涉及 LLM 的提示词（包括但不限于 `Tool Retriever` 的改写 Prompt、`Router` 的决策 Prompt、`Summarizer` 的提取 Prompt、`KG_Manager` 的图谱更新 Prompt 以及 `Generator` 的生成 Prompt）严禁硬编码在 Python 逻辑代码中。
   - 外部配置文件：必须创建一个统一的配置文件（推荐命名为 `prompts.yaml`）来集中存储所有 Prompt 模板。使用 YAML 格式以支持清晰的多行文本。
   - 动态变量注入：在 YAML 模板中必须保留明确的变量占位符（如 `{query}`, `{kg_context}`, `{ltm_context}`, `{tool_schemas}` 等）。在 Python 代码中，需实现一个通用的 `PromptLoader`，并结合 LangChain 的 `ChatPromptTemplate` 等标准生态类，将运行时参数安全、动态地注入到从 YAML 读取的模板中。
    - Prompt 热加载：在 `AdminController` 中提供一个 `reload_prompts()` 的方法，允许系统在不重启的情况下重新读取 `prompts.yaml`，实现提示词的热更新生效。

  `generator` -> `summarizer` + `kg_manager` (异步/并行，不阻塞返回) -> `END`。
